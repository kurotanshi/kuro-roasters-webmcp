# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Branch note**: this is the `vue` branch — the demo is rewritten with the canonical modern Vue
> stack: **Vue 3.5 + Pinia 3 + VueUse + Vite 8**, Single-File Components with `<script setup>`.
> The `main` branch is the original zero-framework / cat-with-markers version. The WebMCP wiring
> is identical between the two; the difference is purely how state and rendering work.

## Project Shape

- `src/` — Vite root.
  - `index.html` is the Vite entry; loads the WebMCP polyfill from `./vendor/...` and `./main.js`.
  - `main.js` does `createApp(App).use(createPinia()).mount('#app')`.
  - `App.vue` is the root layout; it only kicks off WebMCP registration and renders the section components.
  - `data.js` — pure data (`PRODUCTS`, `searchProducts`, `getProduct`, `formatPrice`). Zero Vue/Pinia dependency.
  - `stores/*.js` — 9 Pinia stores. Each uses **setup syntax** (`defineStore('id', () => { ... })`), which looks essentially like a composable but plugs into Pinia's DevTools and avoids `provide`/`inject`.
  - `components/*.vue` — 7 SFCs. Each `import { useXxxStore } from '../stores/...'` directly. State + getters via `storeToRefs()`, actions destructured directly off the store.
  - `style.css` — global styles, imported once from `main.js`.
- `public/vendor/mcp-b-global.iife.js` — committed WebMCP polyfill (~250KB). Vite's publicDir copies it to the build output untouched. Do not replace with a CDN reference; deploys ship it as-is so the demo works offline.
- `index.html` at the repo root and `vendor/` at the repo root are **build artifacts**. **Don't hand-edit them** — they're regenerated by `npm run build`.

Vue, Pinia, and VueUse are real npm dependencies; no CDN.

## Stack rationale

- **Pinia setup stores** look almost identical to plain composables, but every store is a singleton accessed by `useXxxStore()`. That's the most ecosystem-recognizable shape for Vue 3 — anyone who's read the official `pinia` docs immediately knows the pattern. It also removes the `provide`/`inject` plumbing the earlier composable-only version needed.
- **VueUse** replaces hand-rolled state-sync patterns:
  - `useLocalStorage` in `stores/cart.js` and `stores/chat.js` — no manual `watch` + `localStorage.setItem`/`removeItem`. The `apiKey` / `model` / `cart` refs synchronize automatically, and `clear` / `set` events come for free.
  - `useTimeoutFn` in `stores/flash.js` — replaces a `setTimeout` ID dance. `start()` / `stop()` make rapid retriggers behave correctly without leaking pending callbacks.
- **Vite 8** + `@vitejs/plugin-vue` 6 is the current default for new Vue 3.5 projects (`npm create vue@latest` produces this stack).
- **`vite-plugin-singlefile`** keeps the build output as one inlined `index.html` — same "open one file" property as the `main` branch, despite using a real bundler.

## Commands

- `npm run dev` — Vite dev server on port 3000 with HMR. Polyfill served from `public/vendor/`.
- `npm run build` — `vite build` (outputs to `dist/`) → `scripts/postbuild.mjs` flattens `dist/*` to repo root for GitHub Pages. The `dist/` directory is removed at the end.
- `npm run preview` — Vite's static preview of the built artifact.
- No tests, no lint, no typecheck — changes are verified by opening the page in a browser.

## Architecture: stores

The 9 Pinia stores (all setup-syntax, all in `src/stores/`):

| Store id | What it owns | Notable deps |
|---|---|---|
| `cart` | `cart` ref (via `useLocalStorage`), `total` / `itemCount` computed, CRUD actions | data.js |
| `filter` | `filter` reactive (`{ query, origin, roast }`), `filtered` computed | data.js |
| `flash` | `active` reactive (`{ filter, cart }`), `flash(key)` action | `useTimeoutFn` from VueUse |
| `agentLog` / `chatLog` | both registered from the same `logSetup` factory in `stores/logs.js`; each is its own singleton with independent `lines` | — |
| `output` | `text` ref + `show(data)` action — every "show me the result of this" path lands here | — |
| `tools` | `TOOL_DEFS` array, `executeRegisteredTool(name, input)`, `unwrapToolResult(wrapped)` | depends on `cart` / `filter` / `flash` stores |
| `webmcp` | `status` reactive, `waitFor()` polling; calls `navigator.modelContext.registerTool(...)` for each `TOOL_DEFS` entry | depends on `tools` |
| `scenarios` | `running` ref, `run(scenarioId)` action; the `light-roast` / `gesha-checkout` / `reset` scripts | depends on `tools` / `cart` / `filter` / `agentLog` |
| `chat` | Gemini API key / model (both via `useLocalStorage`), `conversation`, `runChatLoop()`, save/clear/reset/send actions | depends on `tools` / `chatLog` |

All cross-store wiring happens inside the setup function (just call the other `useXxxStore()`). No `provide`/`inject` needed for any of these — components import the stores directly.

## Architecture: TOOL_DEFS still has one source of truth

`stores/tools.js` defines `TOOL_DEFS` exactly once. Four call paths all read from it:

1. **Native WebMCP runtime** — `useWebMcpStore().waitFor()` polls until `navigator.modelContext` is available, then registers each `TOOL_DEFS` entry via `registerTool(...)`.
2. **Polyfill fallback** — same registration path; `@mcp-b/global` provides `navigator.modelContext` when the browser lacks it. The polyfill's auto-init checks `navigator.modelContext` first and bails if it already exists, so native (Chrome 146+ Canary with Experimental Web Platform features) is preserved by default. `useWebMcpStore` distinguishes which side won by checking the `__isWebMCPPolyfill` marker on `navigator.modelContext.native`.
3. **Gemini function calling** — `useChatStore.runChatLoop()` maps each `TOOL_DEFS` entry to a Gemini `functionDeclarations` entry (name, description, inputSchema → parameters), then loops up to 6 iterations executing tool calls through `tools.executeRegisteredTool()`.
4. **Manual panel + scripted scenarios** — `ToolPanel.vue` (manual buttons) and `useScenariosStore` (pre-baked scripts) call `tools.executeRegisteredTool()` with a mock client whose `requestUserInteraction(fn)` just runs `fn()` immediately.

Because every tool's `execute` calls into stores (`cart.addToCart`, `filter.applyArgs`, `flash.flash`) that mutate `ref()` / `reactive()` state, Vue's reactivity propagates the changes to every consuming component automatically.

## Architecture: components

Components only consume stores. They never own meaningful state.

| Component | Stores used |
|---|---|
| `StatusBadge.vue` | none — receives `status` as a prop from `App.vue` |
| `ProductSection.vue` | `filter`, `flash`, `cart`, `output` |
| `CartSection.vue` | `cart`, `flash`, `output` |
| `ScenarioPanel.vue` | `scenarios`, `agentLog` |
| `ChatPanel.vue` | `chat`, `chatLog` |
| `ToolPanel.vue` | `tools`, `output` |
| `AgentLogList.vue` | none — pure presentational; takes `lines` + `emptyText` as props |

**`storeToRefs` pattern** — when you destructure state/getters from a store in `<script setup>`, wrap with `storeToRefs()` to keep them reactive. Actions can be destructured directly:

```js
const cartStore = useCartStore();
const { cart, total } = storeToRefs(cartStore);   // refs, reactive in templates
const { addToCart, clearCart } = cartStore;        // plain functions, OK to destructure
```

Without `storeToRefs`, destructured state loses reactivity (because Pinia's store is a Proxy and destructuring just snapshots). This is the canonical Pinia gotcha and the reason every Vue dev recognizes the pattern.

## Build flow gotchas

- `vite-plugin-singlefile` inlines all bundled JS/CSS into one `dist/index.html`. The polyfill `<script src="./vendor/mcp-b-global.iife.js">` is **not** bundled (non-module IIFE on a non-module `<script>` tag); Vite leaves it alone and emits a benign warning during build.
- `outDir: '../dist'` is **outside** the Vite root (`src/`). Don't change to `..` (repo root) — that overlaps `publicDir` and triggers loud Vite warnings about "publicDir inside outDir".
- `scripts/postbuild.mjs` does the `dist/* → repo root` copy so the deploy artifact lives where GitHub Pages expects it. If you reorganize the build output, update this script too.
- `base: './'` in `vite.config.js` is required because GitHub Pages serves at the subpath `kuro.tw/kuro-roasters-webmcp/`. Absolute-rooted asset URLs would 404 in production.

## Deployment

## Editing conventions

- Canonical source is `src/`. Never hand-edit the root `index.html` — re-run `npm run build`.
- When the tool surface changes: append to the `TOOL_DEFS` array inside `useToolsStore()` in `src/stores/tools.js`, include `inputSchema` in JSON-Schema form (Gemini consumes it as `parameters`), mark read-only tools with `annotations: { readOnlyHint: true }`, and have writes go through `client.requestUserInteraction` so the confirmation flow survives under a real Agent runtime.
- New shared state goes into a new or existing Pinia store, not into a free `ref` inside a component. Components should only present state and call actions.
- New components go in `src/components/`. Use `<script setup>` and call `useXxxStore()` for whatever they need.
- Comments and UI copy are in Traditional Chinese (zh-TW). Match that voice when editing.
- This branch demonstrates the WebMCP demo on top of the canonical Vue 3.5 stack. Vue / Pinia / VueUse are bundled locally — **do not switch back to CDN script tags**.
